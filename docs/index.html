When Should Content Be Refreshed?

Comparing transparent rules with logistic regression for content-refresh opportunity scoring.

By Yashika Singh · FlyRank ML Internship

Abstract

This study asks whether logistic regression can improve the prioritization of content that may be experiencing declining search visibility compared with a transparent rules-based baseline. The experiment uses an anonymized starter dataset containing 30,000 content records and 44 columns, with a binary label derived from the recorded trend direction. A logistic-regression classifier is evaluated using a conventional random split and a client-grouped split, and compared with a rules-based score using Precision@20, Precision@50, and average precision. On the random split, logistic regression outperformed the baseline on all three reported metrics; on the client-grouped split, the baseline performed better on both precision-at-K metrics while average precision was similar. These findings support further controlled evaluation of ranked review queues, not a claim that the model generalizes to all clients or that refreshing content causes search-performance recovery.

1. Introduction / Problem Statement

Content teams often have more pages to review than they can manually assess at once. A practical prioritization system should help identify which pages deserve attention first, while remaining transparent enough for a human reviewer to understand and challenge its suggestions.

This project studies one narrow question: does a logistic-regression ranking improve the identification of records labelled as declining compared with a simple rules-based content-refresh score?

The comparison matters because a complex model is not automatically better than a clear heuristic. If the model performs well only when records from the same client appear in both training and testing, its apparent advantage may not transfer to unseen clients. This experiment therefore compares random validation with client-grouped validation.

Central finding: the model's advantage on the random split did not carry over to the client-grouped split. The validation design changes the conclusion.

Exclusions and public-safety choices

The experiment excluded identifiers from model features, the target source and its associated trend percentage, recent-versus-previous 30-day metrics, and the baseline score. These exclusions reduce obvious target leakage and prevent the model from directly using the baseline's output. The exclusions do not prove that all temporal or indirect leakage has been removed.

This public report presents aggregate results and generic methodology only. It does not publish client names, domains, private URLs, raw private search queries, credentials, or a row-level action queue.

3. Methodology

Rules-based baseline

The baseline starts with a transparent score from 0 to 100:

  • Stale: add 40 points when days_since_last_update >= 180.
  • High visibility: add 40 points when impressions_90d is at or above the dataset median.
  • Low click-through rate: add 20 points when ctr is below the dataset median.

For the action playbook, the recorded medians were 731 impressions and 0.07 CTR. These thresholds are dataset-specific operational heuristics, not universal SEO standards.

Logistic-regression model

The target was the binary indicator for a recorded downward trend. Numeric features were search volume, competition, CPC, word count, character count, content age, and days since the last update. Categorical features were competition level, content type, main intent, age tier, freshness tier, word-count tier, and character-count tier.

The model did not use the target source, trend percentage, recent/previous 30-day metrics, identifiers, or baseline score as input features.

The random split tests performance when client patterns can appear on both sides of the split. The grouped split tests a more demanding setting in which the eight held-out test clients do not occur in training. The results are not directly interchangeable because the test sets and their positive rates differ.

Evaluation metrics

  • Precision@20 and Precision@50: the proportion of records labelled as declining among the top 20 or top 50 ranked records.
  • Average precision (AP): a summary of precision across the ranked list.

The available experiment notes do not establish that the target's measurement window is strictly later than every feature window. Temporal leakage therefore remains an unresolved validation risk.

Interpretation

On random validation, logistic regression reached Precision@20 of 0.80 versus 0.75 for the baseline, Precision@50 of 0.74 versus 0.72, and AP of 0.651 versus 0.583. This is a favorable result in a split where 31 clients overlap across training and testing.

On client-grouped validation, the baseline reached Precision@20 of 0.60 and Precision@50 of 0.56, compared with 0.30 and 0.38 for logistic regression. AP was close: 0.520 for the baseline and 0.514 for the model. This does not establish that the model memorized clients, but it does show that the random-split advantage was not robust to this held-out-client test.

No confidence intervals or significance tests are reported here. Differences should be interpreted descriptively, not as proof of statistical significance.

5. Limitations & Honest Framing

  • Starter-data scope: this experiment used 30,000 anonymized rows, not the full 79-million-row warehouse release.
  • Temporal leakage remains unresolved: the exact relationship between feature windows and label construction was not independently verified. A future-time test is still needed.
  • Limited held-out clients: the grouped test contains eight clients. Performance may differ on a broader or different client population.
  • Different split composition: the test positive rates were 54.2% for random validation and 51.7% for grouped validation. Comparisons across the two splits need this context.
  • Observational label: the model predicts a recorded trend label; it does not show that refreshing a page will cause recovery.
  • Heuristic thresholds: the baseline thresholds were derived from this dataset. They may not transfer unchanged to another dataset or operating environment.
  • Operational review required: a ranked score is a triage aid, not an automatic instruction to rewrite or republish content.

This is an exploratory model comparison. It does not prove Google's ranking mechanisms, establish causal effects, or validate production readiness.

6. Ranked Recommendations

The action playbook turns observed signals into a human-review workflow. Its thresholds are prioritization heuristics, not predictions of guaranteed recovery.

Action counts are from the generated playbook: 30,000 records total. The labels describe workflow recommendations, not confirmed business outcomes.

Suggested review sequence

  1. Check the priority queue manually and verify the underlying signals.
  2. For stale pages, compare the page's purpose and accuracy with current user needs before editing.
  3. For high-impression, low-CTR pages, review the search result presentation and query intent before rewriting the main content.
  4. Record the reason for each decision and monitor subsequent performance using a clearly defined time window.
  5. Evaluate any future model using a time-aware holdout and a client-grouped split before relying on it operationally.

The grouped validation results favor keeping the transparent baseline as the reference point until a better model demonstrates robust performance on held-out clients and future time periods.
